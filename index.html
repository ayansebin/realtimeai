      How it works
      
Granite reads the signal. Confluent supplies the context, the governance and the delivery.

      
Confluent Cloud provides native inference: the models are hosted by Confluent and called from Flink SQL. Inference results are written to Kafka topics and shared with fanout, consumable by alerting systems, dashboards, lakehouses and AI agents.

      Flink SQL
      
The whole project is one call.

      
Both functions are windowed aggregates: OVER (ORDER BY event_time RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW). Add PARTITION BY to keep one model context per card, SKU, host or asset. Change the model value and the same statement runs any of the four Granite models, or TimesFM, with no pipeline redesign.

    


    

      
      
      
      
      
    


    

      
Twelve steps ahead on a meter reading stream with the default model. The result is a ROW with a forecast array (one entry per horizon step, each with mean, q10, q50 and q90) and a metadata JSON string.

      
AI_FORECAST · ttm
SELECT
  event_time,
  load_kw,
  AI_FORECAST(
    load_kw,
    event_time,
    JSON_OBJECT('model' VALUE 'ttm', 'horizon' VALUE 12)
  ) OVER (
    PARTITION BY meter_id
    ORDER BY event_time
    RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
  ) AS forecast
FROM meter_readings;

    


    

      
A 99 percent prediction interval on service latency. Each row returns actual_value, forecast_value, lower_bound, upper_bound, is_anomaly and a rolling rmse. Fields are null until minContextSize points have arrived.

      
AI_DETECT_ANOMALIES · flowstate
SELECT
  event_time,
  response_ms,
  AI_DETECT_ANOMALIES(
    response_ms,
    event_time,
    JSON_OBJECT(
      'model' VALUE 'flowstate',
      'minContextSize' VALUE 20,
      'maxContextSize' VALUE 512,
      'confidencePercentage' VALUE 99.0
    )
  ) OVER (
    PARTITION BY host_id
    ORDER BY event_time
    RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
  ) AS anomaly
FROM server_metrics;

    


    

      
The fraud pattern: a sense of normal per card, scored while the payment is in flight, and only the flagged rows written to an alerts topic that a case system, a dashboard or a Streaming Agent consumes.

      
CREATE TABLE AS SELECT · ttm
CREATE TABLE card_alerts AS
SELECT
  card_id,
  event_time,
  amount,
  anomaly.forecast_value AS expected,
  anomaly.lower_bound,
  anomaly.upper_bound,
  anomaly.rmse
FROM (
  SELECT
    card_id,
    event_time,
    amount,
    AI_DETECT_ANOMALIES(
      amount,
      event_time,
      JSON_OBJECT('model' VALUE 'ttm', 'confidencePercentage' VALUE 99.5)
    ) OVER (
      PARTITION BY card_id
      ORDER BY event_time
      RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
    ) AS anomaly
  FROM card_payments
)
WHERE anomaly.is_anomaly = TRUE;

    


    

      
The planner's pattern: a seven-day probabilistic forecast per SKU with PatchTST-FM, unnested to one row per horizon step so replenishment can read the 90th percentile as a reorder point.

      
AI_FORECAST + UNNEST · patchtstfm
SELECT
  s.sku,
  s.event_time AS as_of,
  step.`timestamp` AS forecast_day,
  step.q10 AS floor,
  step.q50 AS expected,
  step.q90 AS reorder_point
FROM (
  SELECT
    sku,
    event_time,
    AI_FORECAST(
      units_sold,
      event_time,
      JSON_OBJECT(
        'model' VALUE 'patchtstfm',
        'horizon' VALUE 7,
        'maxContextSize' VALUE 730
      )
    ) OVER (
      PARTITION BY sku
      ORDER BY event_time
      RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
    ) AS f
  FROM daily_sales
) AS s
CROSS JOIN UNNEST(s.f.forecast) AS step (`timestamp`, mean, q10, q50, q90);

Four architectures, four papers

    
Each family comes from peer-reviewed research, with weights, code and benchmark reproductions published alongside.



  
2024TTMTiny Time Mixers: fast pre-trained models for zero and few-shot forecasting. NeurIPS 2024. Lightweight MLP-Mixer backbone, channel independent, tiny footprint.

  
2025FlowStateSampling-rate-equivariant forecasting. ICML 2026. State-space encoder with a functional basis decoder, so one model generalizes across sampling rates.

  
2026PatchTST-FMRevisiting the generic transformer. Patched transformer backbone trained supervised and self-supervised, scaling with generic attention.

  
2026TSPulseTiny pre-trained models with disentangled representation. ICLR 2026. Time and frequency embeddings with dual decoders, one backbone for many tasks.

      Agents
      
Agents run the loop. Experts approve at every gate.

      
Two layers of agents, both on Confluent. At build time, coding agents work through Confluent's managed MCP servers, scoped by your RBAC and written to the audit log. At run time, the loop becomes Streaming Agents in Flink SQL. Every pass learns from live data, and a person signs off before anything changes.

    

    

      
Stage 1
Data prep
Streams profiled and aligned.
Topics, schemas and samples through Confluent MCP, then Flink SQL joins, windows, resampling and gap fill. Schema Registry contracts guarantee the shape of every stream.
Gate: validate the data and the demand drivers

      
Stage 2
Model use
Zero shot first. Fine-tune if it pays.
TTM for throughput, PatchTST-FM for long context and probabilistic output, TSPulse for detection and search. LoRA fine-tuning only when the backtest shows it pays.
Gate: approve the model choice

      
Stage 3
Benchmark
Backtest, champion-challenger.
Rolling backtests on MASE, WAPE and CRPS against a seasonal naive baseline and the incumbent model, with champion-challenger before promotion.
Gate: sign off accuracy and bias

      
Stage 4
Deploy
A versioned Flink SQL function.
CREATE TOOL wraps AI_FORECAST or AI_DETECT_ANOMALIES, CREATE AGENT binds a model, prompt and tools, AI_RUN_AGENT executes per event and agents chain. Under RBAC, billed as Flink compute.
Gate: approve the release and its guardrails

      
Stage 5
Learn
Drift watched, retuned.
Actuals joined to forecasts in the stream, bias and drift tracked, and a drafter-critic reflection reviews before any retune is triggered.
Gate: review drift before retraining

      Why the stream
      
The decision window closes faster than the batch job runs.

      
Most forecasting and detection still runs on old economics: one bespoke model per series and months of expert work on each. So teams model the few hundred series where the money is and cover the rest with safety stock, extra headroom and wider tolerances, acted on after the window has closed. That margin is the cost of a decision nobody could forecast, paid every cycle.

    

    

      
      

        
A time series foundation model changes the economics. Trained once across vast, varied signals, it generalizes to a series it has never seen. Give it a window of measurements and it returns what comes next, how far behaviour sits from normal, which history looks like this one, and which settings best serve a target. A demand planner, a fraud analyst or a process engineer can put it to work on their own streams.

        
Forecasting and detection are stateful. The next value only means something against recent history, and an anomaly only exists against a running sense of normal. Flink manages that state, keyed per series and fault tolerant, so every model call gets the history it needs without a separate data store or a database hit per event.

        
Score in the stream. Train, backtest and evaluate at rest.
The lakehouse stays the right place for bulk historical scoring, backtesting and fine-tuning. Tableflow lands inference results from Kafka topics as Iceberg or Delta Lake tables for exactly that, so the two estates share one lineage.

      

    


    

      

        Demand planner, grocery retail
        
She plans the head of the catalogue. The tail sits on the shelf as working capital.

        

          
Pain
One model per SKU, refit by hand, so planning never reaches the long tail. New launches start with no history at all.

          
Wants
One shared model across 100,000 SKUs nightly on CPU, returning a distribution rather than a single line, so service level becomes a policy she can state out loud.

          
Outcome
Reorder points off the 90th percentile. Fewer stockouts and markdowns. Freed working capital, usually the largest line in the business case.

        

      

      

        Fraud lead, retail bank
        
Rules are enumerable, so adversaries enumerate them. Labels are scarce and stale.

        

          
Pain
Tightening a rule declines more honest customers. Bespoke models wait for labelled cases that arrive late, and false alarms cost more than the crime.

          
Wants
A sense of normal per card, scored while the payment is in flight, that transfers to new products and corridors on day one.

          
Outcome
The alarm fires before the money moves. The same customer on an honest holiday sails through. Every score becomes a trigger: block, escalate with the closest past cases attached, or hand to an agent.

        

      

      

        Process engineer, consumer goods plant
        
Statistical models drift. Rule-based control holds a setpoint but never improves it.

        

          
Pain
Months of bespoke modelling per line, and recommendations nobody can interrogate, so optimization stays in pilots and the plant runs on margins.

          
Wants
A forecast conditioned on the settings the crew controls, so it becomes a simulator and an optimizer searches it against a KPI he names, inside his constraints.

          
Outcome
Months become days. One point on an operation turning over hundreds of millions is a seven-figure line, and the person who knows the line steers it.

Quickstart on a test table

        
Creates a sensor table, inserts an hour of readings with one injected spike, then runs anomaly detection with the default model. Copy all three statements into a Flink SQL workspace and run them in order.

        
    
          
  • The first 19 rows return null output fields because minContextSize defaults to 20.
    • 
          
  • A yellow MISSING_PARTITION_BY warning is a performance hint. For one test series it is safe to ignore. Add PARTITION BY for real multi-series topics.
    • 
          
  • The injected 10:45 reading should return is_anomaly = TRUE.
    • 
        

      

      
Flink SQL · quickstart
-- 1. A table with a timestamp and a value
CREATE TABLE sensor_test (
  sensor_id STRING,
  temp_c DOUBLE,
  event_time TIMESTAMP(3),
  WATERMARK FOR event_time AS event_time - INTERVAL '5' SECOND
);

-- 2. An hour of readings, one spike at 10:45
INSERT INTO sensor_test VALUES
  ('line-1', 31.4, TIMESTAMP '2026-10-16 10:00:00.000'),
  ('line-1', 31.6, TIMESTAMP '2026-10-16 10:01:00.000'),
  ('line-1', 31.5, TIMESTAMP '2026-10-16 10:02:00.000'),
  -- ... one row per minute, values between 31.2 and 31.9 ...
  ('line-1', 34.9, TIMESTAMP '2026-10-16 10:45:00.000'),
  -- ... back to normal through 10:59 ...
  ('line-1', 31.5, TIMESTAMP '2026-10-16 10:59:00.000');

-- 3. Score every reading against its own history
SELECT
  event_time,
  temp_c,
  AI_DETECT_ANOMALIES(
    temp_c,
    event_time,
    JSON_OBJECT('model' VALUE 'ttm', 'confidencePercentage' VALUE 99.0)
  ) OVER (
    PARTITION BY sensor_id
    ORDER BY event_time
    RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
  ) AS anomaly
FROM sensor_test;

Questions
What people ask before they enroll.

    

      
Is this production-ready?
Early Access features are for evaluation and non-production testing. They are provided without support, SLA or indemnification while Confluent and IBM gather feedback, and general availability follows. Many clients run them on a copy of a production topic to validate value before GA.

      
What does it cost?
There is no charge for the models during Early Access. Flink compute for the statements you run is billed in CFUs as part of your compute pool, like any other Flink SQL. There are no model-serving instances to pay for and no cloud ingress or egress fees for inference.

      
Which clouds and deployments?
Early Access runs on Confluent Cloud for Apache Flink on AWS. Confluent Platform follows, bringing the same models and capabilities to on-premises and hybrid environments, which is where most industrial deployments live.

      
Can I bring my own model?
Not through AI_FORECAST and AI_DETECT_ANOMALIES, which use models hosted and managed by Confluent. For a custom or remote model, register it with CREATE MODEL and call it with ML_PREDICT. During Early Access you can also ask your Confluent representative for additional time series models to be made available.

      
Where does my data go?
Inference runs inside Confluent Cloud, in the same environment as your Flink statements, and follows the RBAC and privacy policies already applied to your topics. Nothing is extracted to a separate ML platform.

      
What about multivariate series?
Each AI_FORECAST or AI_DETECT_ANOMALIES call scores one value column, and PARTITION BY gives every entity its own context. For multivariate robust detection today, ML_DETECT_ANOMALIES_ROBUST accepts a ROW of metrics. Cross-channel modelling through fine-tuning is part of the Granite Time Series library, and multivariate functions are one of the most common requests shaping the roadmap. Tell us yours.

      
How is this different from ML_FORECAST and ML_DETECT_ANOMALIES?
ML_FORECAST and ML_DETECT_ANOMALIES fit an ARIMA model per stream and expose p, d and q. AI_FORECAST and AI_DETECT_ANOMALIES use pretrained foundation models: no training phase, zero-shot on an unseen series, quantiles in the output, and a model choice you can benchmark with one parameter.

      
Under which licenses are the models released?
TTM, FlowState and TSPulse are released under Apache 2.0. PatchTST-FM-r2 is released under the OpenMDW license, which is commercial-friendly. Weights, architecture, inference pipeline and the code to reproduce the benchmark results are on Hugging Face and GitHub.

      
Can I run the models outside Confluent?
Yes. The open weights run on your own CPUs through the granite-tsfm library, which is the right place for backtesting, bulk historical scoring and fine-tuning. The Confluent integration removes the serving, the wiring and the state management for scoring in the stream.
